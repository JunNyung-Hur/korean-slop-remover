# 릴리즈 노트

일반 사용자가 쓰는 서비스의 릴리즈 노트를 말한다. 실제 교정 사례 한 번을 바탕으로 쓴 기준이라, 쓰다가 어색한 결과가 나오면 이 파일부터 고친다.

## 독자

서비스를 쓰는 사람이다. 지난번과 무엇이 달라졌는지, 내가 쓰던 기능이 바뀌었는지만 확인하고 닫는다. 어떻게 만들었는지는 궁금해하지 않는다.

## 구성

1. 이번 버전에서 달라진 것을 한두 문장으로 요약한다.
2. 주요 변경을 몇 개 쓴다. 변경마다 사용자가 화면에서 겪는 변화를 쓰고, 어디서 무엇을 누르면 되는지까지 적는다.

이 둘로 끝낸다. 운영이나 개발에 필요한 정보는 릴리즈 노트가 아닌 곳에 둔다.

## 넣지 않는 것

- 마이그레이션, DB 변경, 배포 절차
- "기존과 동일합니다", "동작 변화는 없습니다", "로그인이 필요합니다"처럼 달라진 게 없다는 말
- 헤더 이름, 엔드포인트 같은 내부 식별자와 내부 동작 설명
- 커밋 메시지를 그대로 옮긴 목록
- "세부 기술 변경은 변경 이력을 참고해 주세요" 같은 다른 문서 안내

라이브러리나 API처럼 독자가 개발자인 경우는 다르다. 호환성이 깨지는 변경과 옮겨 가는 방법이 곧 독자가 겪는 변화라서 빠지면 안 된다.

## 말투

~합니다체로 쓴다. 변경은 사용자가 할 수 있게 된 일로 쓴다.

## 제목, 굵은 글씨, 그림

- 제목은 버전과 날짜, 그 아래 "주요 변경" 정도면 충분하다. "사용자 영향", "참고 사항" 같은 구획을 관례처럼 세우지 않는다.
- 굵은 글씨는 변경 항목의 이름에만 쓴다.
- 화면이 눈에 띄게 바뀌었으면 바뀐 화면의 스크린샷 하나를 붙인다.

## 자주 나오는 슬롭

- "이번 릴리즈에서는 다양한 개선이 이루어졌습니다"로 시작한다.
- "성능 개선", "안정성 향상"처럼 사용자가 무엇을 겪는지 알 수 없는 항목을 쓴다.
- 바뀌지 않은 것을 "기존 기능은 그대로 유지됩니다"로 안심시킨다.
- 내부 구조를 바꾼 일을 변경 항목으로 올린다.

## 예시

> # v2.3 (11월 3일)
>
> 녹음이 중간에 끊겨도 이어서 녹음할 수 있게 되었고, 회의록을 동료와 공유할 때 권한을 나눠 줄 수 있게 되었습니다.
>
> ## 주요 변경
>
> **이어서 녹음**
>
> 녹음 중에 실수로 창을 닫거나 새로고침해도 녹음이 사라지지 않습니다. 회의를 다시 열면 나오는 이어서 녹음 버튼을 누르면 멈춘 지점부터 다시 녹음됩니다.
>
> **공유 권한**
>
> 회의록 오른쪽 위의 공유 버튼에서 동료를 추가할 때 보기만 가능, 편집 가능 중 하나를 고를 수 있습니다.
