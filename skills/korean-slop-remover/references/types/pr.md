# PR

실제 교정 사례 없이 쓴 초안이다. 쓰다가 어색한 결과가 나오면 이 파일부터 고친다.

## 독자

리뷰어다. diff를 옆에 띄워 놓고 읽는다. 무엇이 바뀌었는지는 diff에 다 있으니, diff만 봐서는 모르는 것을 알고 싶어 한다.

## 구성

1. 첫 문장에 무엇을 바꿨는지 쓰고 관련 이슈를 링크한다. 배경은 이슈에 있으면 다시 쓰지 않는다.
2. diff만 봐서는 알 수 없는 결정과 이유를 쓴다. 왜 이 방식인지, 일부러 하지 않은 것은 무엇인지.
3. 리뷰어가 특히 봐야 할 곳을 짚는다. 동작이 바뀌는 곳, 위험한 곳, 확신이 없는 곳이다.
4. 어떻게 확인했는지 쓴다. 돌린 테스트, 직접 해 본 동작, 리뷰어가 재현하는 방법이다.

## 말투

저장소에서 쓰던 말투를 따른다. 정해진 게 없으면 한다체로 짧게 쓴다.

## 제목, 굵은 글씨, 그림

- 짧은 PR은 제목 없이 문단 몇 개로 끝낸다. 길어지면 "변경", "확인 방법" 정도로만 나눈다.
- 굵은 글씨는 리뷰어가 꼭 봐야 할 위험 한 곳에만 쓴다.
- 화면이 바뀌면 그림 대신 바뀌기 전과 후의 스크린샷을 붙인다.

## 자주 나오는 슬롭

- "이 PR은 ~를 개선합니다"로 시작한다.
- 파일별 변경 내용을 다시 나열한다. diff에 다 있다.
- "주요 변경 사항" 아래 3단 불릿을 단다.
- "테스트를 완료했습니다"만 있고 무엇을 확인했는지 없다.
- 이슈에 있는 배경을 그대로 다시 옮긴다.

## 예시

> 업로드 크기 제한을 서버로 옮겼다. #42
>
> 제한값은 `MAX_UPLOAD_MB` 하나로 두고 nginx 값은 그보다 10MB 크게 잡았다. nginx에서 먼저 끊기면 사용자가 제한값을 볼 수 없어서다. 파일 종류별 제한은 이슈에서 이야기한 대로 이번에는 넣지 않았다.
>
> **기존 업로드 API를 직접 부르는 내부 스크립트가 있으면 413을 받게 된다.** 검색해 보니 `scripts/import_minutes.py` 하나라 같이 고쳤다.
>
> 41MB 파일로 웹 업로드와 API 직접 호출 둘 다 413이 나오는 것을 확인했다. 39MB는 그대로 올라간다.
